# 概要

## 解く問題

1 PR に再現テストと修正をまとめると、CI が Green でも「テストが修正前に落ちていたか」は履歴からは分からない。
レビュアーがローカルで修正を巻き戻して確認する負荷が残る。

## 2層スタックの形

```
main
└─ PR 1（下層）: 再現テストのみ（成否反転で CI は Green）
   └─ PR 2（上層）: 実装修正 + 反転の解除（通常テストで CI Green）
```

- **論理上の Red**: 通常実行ではテストが失敗する状態（下層の内容）
- **論理上の Green**: 同じテストが実装修正後に成功する状態（上層の内容）
- **CI の見え方**: 反転 API により下層・上層とも CI 表示は Green になり得る。Red→Green は「2つの PR の CI 結果と diff」を並べて読む

## CI が保証するもの・しないもの

| 保証する | 保証しない |
| --- | --- |
| 下層: 現行コードでそのテストが失敗する（反転により Pass 扱い） | 失敗理由が対象の不具合であること（アサーション失敗でも型エラーでも下層は Green になり得る） |
| 上層: 同じテストが修正後に成功する | テストがフレークでないこと（向き不向きは [limitations-and-fit.md](limitations-and-fit.md)） |

失敗理由の妥当性は PR 1 の diff を人が読んで判断する。手元での巻き戻し確認より負荷は小さい。

## 単一 PR・コミット分割との違い

- 同一 PR 内のコミット分割: CI は通常 head だけを検証し、中間コミットの Red は履歴に残らない
- squash merge: PR 単位ならスタックは PR ごとにスカッシュコミットが残り、再現と修正を `main` 上でも分けて辿れる（[gh-stack](../../../gh-stack/SKILL.md) のマージ手順に従う）
