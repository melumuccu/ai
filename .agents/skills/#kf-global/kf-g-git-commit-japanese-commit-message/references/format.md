# 出力形式と基本ルール

本文の `概要` / `Why` の定義は本ファイルを正（SoT）とする。

## 出力形式

- 1行目は `<type_>: <カテゴリ> > <subject>` にする
- 2行目は必ず空行にする
- 3行目以降に本文を書く
- 本文は箇条書きで書く
- 少なくとも `- 概要` と `- Why:` を含める

## 本文の書き方

### 概要（What）

- `概要` には何を変えたか（What）を書く
- subject が示す主目的の再述だけに留めない。必要なら具体箇所や要点を補う

### Why（判断理由）

- `Why` にはなぜこのように実装・変更したか（判断理由）を書く
- subject / 概要 / diff が既に示す変更内容（What）の再述は Why に書かない
- 必要に応じて次を含める
  - 根本原因
  - 制約
  - 設計判断
  - 却下した代替案

### 共通

- 1行で収まるなら短くまとめる
- 複数点ある場合や長くなる場合は、配下の箇条書きへ分ける
- 理由と背景は混ぜすぎない

## subject の書き方

- 日本語で書く
- 先頭にカテゴリを置き、主目的との間を ` > ` で区切る
- カテゴリは変更対象を短く表す語にする
- カテゴリ例は `skills`、`prompts`、`認証`、`設定画面` など
- ` > ` の後ろに変更の主目的を書く
- 変更の主目的を1つに絞る
- 冗長な前置きは入れない
- 文末の句点は付けない
- 体言止めを優先する
- 敬語は使わない
- 「修正対応」「対応を実施」のような曖昧表現を避ける
- 何を変えたかが分かる語にする

### 良い例

- `fix__: 検索 > 検索結果0件時のローディング終了不備を修正`
- `refa_: 認証 > サービス層分離`
- `docs_: README > 開発環境構築の前提条件を追記`

### 避ける例

- `fix__: いろいろ修正`
- `fix__: 検索結果0件時のローディング終了不備を修正`
- `chore: 対応`
- `feat_: skills > プロンプト改善`

## 文体

- 一文を短く保つ
- 接続詞や前置きを最小限にする
- 体言止めを多用する
- 全体を端的に保つ
