# Why not

## 基本方針

- コード内コメントは常に Why not だけ書く。What は命名・型・テストから読み取れる前提にする
- コメントは、コードだけでは読めない却下理由や誤変更防止の文脈を未来の作業者に渡すためのもの
- 処理内容の説明が必要に見えるなら、まず命名、関数分割、型、テストで読みやすくできないかを優先する
- 採用した実装の positive Why（なぜこの方式を選んだか）は commit log が担う。コメントには書かない

## コメントしてよい内容

次のような、コードから読み取れない却下理由や誤変更防止だけをコメントに残す。

- なぜ単純に見える別実装を採らなかったか
- なぜ一見不要な処理を削除できないか
- なぜこの順序、条件分岐、待機、再試行、フォールバックを単純化できないか
- なぜ互換性、性能、セキュリティ、運用上の制約のため別案を却下したか
- なぜ外部サービス、ブラウザ、Docker、ファイル形式などの癖に合わせる必要があり、素直な実装へ置き換えられないか
- 過去の不具合や回帰を避けるため、削除・置換してはいけない理由

## コメントしない内容

次の内容は書かない。既にある場合は、周辺変更の範囲で削除または Why not に置き換える。

- 採用した実装の positive Why（なぜこのライブラリ、API、依存関係を選んだか）
- 関数名、変数名、型、制御構造を読めば分かる処理説明（What）
- `if`、`map`、`filter`、`return` などの逐語的な説明（How）
- 「画像を変換する」「レスポンスを返す」などコードと同じ粒度の説明
- 実装と同期し続ける必要があるだけのコメント
- TODO の形をした曖昧な願望や、担当者の意図が分からないメモ

## 判断手順

コメントを追加または維持する前に、次を確認する。

1. そのコメントは Why not（別案の却下、単純化・削除不能）を説明しているか
1. positive Why（採用理由）になっていないか
1. コメントなしだと、将来の作業者が誤って削除、単純化、置換しそうか
1. コードの命名や構造を改善するほうが自然ではないか

1 つ目が満たせない場合、そのコメントは書かない。2 つ目に該当する場合、commit log へ移す。4 つ目が自然な場合、コメントよりコード改善を優先する。

## 例

避ける（What）:

```ts
// 画像を JPEG に変換する
const converted = await convertToJpeg(image);
```

避ける（positive Why）:

```ts
// HEIC はブラウザ表示が不安定なため、JPEG に寄せる。
const converted = await convertToJpeg(image);
```

よい（Why not）:

```ts
// ブラウザの HEIC 表示は環境差が大きく、素直な `<img>` 表示へ戻すと未対応環境で壊れるため JPEG へ寄せる。
const converted = await convertToJpeg(image);
```

避ける（What）:

```ts
// アセット ID がなければ 400 を返す
if (!assetId) {
  return error(400, "assetId is required");
}
```

よい（Why not）:

```ts
// Immich API への空 ID 転送は 500 として返るため、利用者向けにはここで入力エラーに正規化する。
if (!assetId) {
  return error(400, "assetId is required");
}
```

## レビュー時の扱い

- What コメントを見つけたら削除候補として扱う
- positive Why コメントを見つけたら commit log へ移す候補として扱う
- Why not が必要なのにコメントがない場合は、コメント追加だけでなく、より明確な名前や構造にできないかも確認する
